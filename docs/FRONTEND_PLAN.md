# План реализации фронтенда GameScope

План основан на текущем контракте из [`API.md`](./API.md). Сейчас каталог `frontend/` пуст, поэтому реализация начнётся с создания React-приложения.

## 1. Цель и границы

Сделать адаптивный интерфейс каталога игр с тремя основными сценариями:

1. Найти игру по названию.
2. Открыть карточку выбранной игры и посмотреть доступные сведения и оценки.
3. Открыть отзывы Steam, если backend может их предоставить.

Фронтенд использует только публичные GET-эндпоинты GameScope. Авторизация не нужна. Ключи RAWG и других поставщиков остаются на backend. Не включать в первую версию функции, для которых API пока не предоставляет контракт: аккаунты, избранное, персональные списки, рекомендации, AI-сводки/чат и внешние ссылки на покупку.

## 2. Маршруты и пользовательские сценарии

- `/` — поиск и результаты. Текст запроса синхронизируется с `?q=...`, чтобы поиск можно было обновить, скопировать и восстановить кнопкой браузера.
- `/games/:id` — подробная карточка игры. `id` всегда внутренний ID GameScope из `items[].id`.
- `/games/:id/reviews` — отдельный экран отзывов; ссылка на него также показывается на карточке.
- Неизвестный маршрут показывает аккуратную страницу «Страница не найдена» и ссылку к поиску.

Поток: пользователь вводит название → фронтенд запрашивает поиск → выбирает результат → фронтенд получает карточку по внутреннему ID → при переходе к отзывам запрашивает отзывы для того же ID. Внешние `rawg`/`steam` ID никогда не подставляются в URL GameScope.

## 3. Технологии и структура

- React + TypeScript + Vite.
- React Router для маршрутов и навигации.
- TanStack Query для состояния серверных данных, кэша, отмены устаревших запросов и повторного использования уже загруженных карточек.
- `fetch` без отдельной HTTP-библиотеки; общий API-клиент централизует базовый URL, JSON, обработку HTTP-ошибок и `AbortSignal`.
- CSS Modules или обычный CSS с переменными дизайн-системы; не добавлять тяжёлую UI-библиотеку для небольшого каталога.
- Vitest + React Testing Library для проверки API-клиента и ключевых пользовательских состояний.

Предлагаемая структура:

```text
frontend/
  .env.example
  index.html
  package.json
  vite.config.ts
  src/
    app/                 # приложение, маршруты, провайдеры
    api/                 # типы контракта, fetch-клиент, методы games
    components/          # общие оболочка, поиск, состояния, метаданные
    features/
      search/            # страница поиска и сетка результатов
      game/              # карточка и секции игры
      reviews/           # список и элемент отзыва
    styles/              # глобальные токены и базовые стили
    test/                # настройка тестовой среды и тесты
```

Базовый адрес задаётся через `VITE_API_BASE_URL`, с локальным значением по умолчанию `http://127.0.0.1:8000`. В браузер не добавляются секреты поставщиков. Локальный Vite origin должен быть `http://localhost:5173` либо `http://127.0.0.1:5173`, разрешённым текущей настройкой CORS backend.

## 4. Клиент API и модели

В `src/api/` определить типы, совпадающие с документом: `Game`, `GameRating`, `GamePrice`, `GameSystemRequirements`, `GameReview` и `GameReviewsResponse`. Поля, объявленные API nullable, типизировать как nullable; для жанров, платформ, рейтингов и прочих коллекций учитывать пустые массивы.

Методы клиента:

- `searchGames(query, limit = 20)` → `GET /api/games/search?q=...&limit=...`.
- `getGame(id)` → `GET /api/games/{id}`.
- `getGameReviews(id, limit = 20)` → `GET /api/games/{id}/reviews?limit=...`.
- Опциональный `getHealth()` использовать только в локальной диагностике/инструментах разработки, не как условие показа приложения: `/health` сообщает о запуске HTTP-приложения, но не проверяет БД и поставщиков.

Параметры query формировать через `URLSearchParams`; ID кодировать как компонент URL. Клиент проверяет `response.ok`, безопасно разбирает JSON-ошибки и выбрасывает единый `ApiError` с HTTP-статусом и доступным сообщением. Ошибки парсинга/сети также превращаются в понятную ошибку клиента. Все запросы принимают `AbortSignal` от TanStack Query.

Ключи кэша: `['games', 'search', normalizedQuery]`, `['games', id]`, `['games', id, 'reviews', limit]`. Поиск запускается только для непустого запроса после trim; поле ограничивается 200 символами. Результат поиска ограничить `limit=20`: провайдер RAWG сейчас не гарантирует больше 20 результатов, даже если запросить до 100.

## 5. Экраны и поведение интерфейса

### Поиск и каталог

- Главная страница содержит верхнюю навигацию GameScope, заметное поле поиска и адаптивную сетку карточек.
- Применять debounce около 300 мс, отменять запрос к старому значению и не запрашивать API на каждый промежуточный символ.
- При изменении URL `?q=...` восстанавливать значение поля и результаты поиска.
- Карточка результата показывает обложку (или заглушку), название, дату релиза, доступные платформы, несколько жанров и оценки с явной подписью источника и шкалы.
- Обрабатывать состояния: начальное приглашение к поиску, загрузка, совпадений нет, ошибка, результаты. При очистке строки очищать результаты и query-параметр.
- Не добавлять пагинацию: API не поддерживает offset/cursor.

### Карточка игры

- Сверху показывать обложку, название, дату релиза, жанры и платформы.
- Отдельные секции: описание, разработчики и издатели, категории, оценки, цена/бесплатность, достижения, системные требования.
- Не объединять оценки разных источников в среднее значение. Для каждой показывать `score / max_score`, источник и количество оценок, если оно известно.
- Скрывать секции без содержимого или показывать короткий текст «Данные недоступны». Различать `is_free: true`, `false` и `null`; отсутствие цены не трактовать как бесплатность.
- Описание и требования отображать как текст, не исполнять HTML, полученный извне.
- Показывать заметную ссылку на отзывы; при отсутствии `id` не строить ссылку на API и сообщить, что для этой карточки нельзя загрузить детали.

### Отзывы

- Каждый отзыв показывает текст, голос «рекомендует/не рекомендует», дату, язык, время в игре и автора, когда значения доступны.
- Начальная загрузка — 20 отзывов. Так как API не поддерживает постраничную выборку, «Показать ещё» при необходимости повышает `limit` (например, до 40, 60 и далее максимум до 100) и получает увеличенный список заново. Интерфейс не должен обещать доступ к `total` отзывам: это общее число у Steam, а не число загружаемых страниц.
- Пустой список при успешном ответе — штатное состояние (например, Steam ID не связан); отдельно показывать ошибки запроса.

### Визуальные и доступностные требования

- Сдержанная тёмная тема каталога игр с контрастными поверхностями, заметными фокус-состояниями и предсказуемыми компонентами.
- Сначала адаптация для мобильного экрана: одна колонка на узком экране, затем сетка с несколькими колонками; карточка игры и отзывы не должны вызывать горизонтальную прокрутку.
- Использовать семантические заголовки, кнопки и ссылки; все действия доступны с клавиатуры, поле поиска имеет label, изображения — осмысленный alt либо пустой alt для декора.
- Длинные описания, системные требования и отзывы переносить; неизвестные изображения заменять заглушкой.

## 6. Порядок реализации

### Этап 1 — основание приложения

Создать Vite-проект React/TypeScript в `frontend/`, настроить маршруты, TanStack Query, глобальные стили, конфигурацию API URL, команды `dev`, `build`, `test` и `lint`/проверку TypeScript. Добавить `frontend/.env.example` и короткую инструкцию запуска. Результат этапа — приложение запускается и строится без ошибок, маршруты отображают каркас.

### Этап 2 — API-слой и поиск

Ввести типы контракта, клиент запросов и единое преобразование ошибок. Реализовать синхронизацию строки поиска с URL, debounce, отмену устаревших запросов, сетку результатов и состояния загрузки/пустого ответа/ошибки. Проверить запросы к API, кодирование параметров и валидацию границ.

### Этап 3 — подробная карточка

Подключить получение игры по внутреннему ID и собрать секции карточки из доступных nullable-полей. Добавить кэширование и повторное использование результатов поиска, обработку 404 и отсутствие рейтингов/цены/изображения/требований. Проверить прямую загрузку маршрута и обновление страницы.

### Этап 4 — отзывы Steam

Добавить страницу отзывов, пустое состояние, отображение необязательных полей и увеличение `limit` до 100. Проверить игру без Steam-связи, ошибку поставщика и различие `items.length` и общего `total`.

### Этап 5 — адаптивность и доводка

Проверить мобильную и широкую раскладки, клавиатурную навигацию, длинные тексты, недоступные изображения, браузерную историю и сообщения об ошибках. Запустить тесты, TypeScript-проверку и production build; устранить найденные ошибки до передачи результата.

## 7. Обработка состояний и ошибок API

| Ситуация | Поведение интерфейса |
|---|---|
| Поиск вернул `items: []` | Сообщить, что совпадений нет, предложить изменить запрос. |
| Поля Game равны `null` или массив пуст | Скрыть соответствующее значение либо показать нейтральную заглушку; не показывать `null`, `undefined` и ложные данные. |
| `404` на деталях/отзывах | Показать «Игра не найдена» и ссылку на поиск. |
| `422` | Для поиска подсветить/объяснить недопустимый запрос; для иных случаев — общее сообщение о некорректном запросе. |
| `502` / `503` | Сообщить, что источник данных временно недоступен; предложить повторить запрос. Кэшированная карточка, если уже была, остаётся доступной согласно поведению backend. |
| `500`, некорректный ответ или сетевая ошибка | Показать общее сообщение без внутренних деталей сервера и кнопку повтора. |
| Нет отзывов (`200`, пустой `items`) | Показать штатное сообщение, что отзывы сейчас недоступны для этой игры. |

Ошибку отображать рядом с затронутым содержимым. Повтор запроса не должен сбрасывать уже введённый поиск или ломать навигацию.

## 8. Критерии готовности первой версии

- Поиск отправляет только нормализованный непустой `q`, показывает максимум один ответный набор и поддерживает ссылку с `?q=`.
- Выбор результата открывает детали по `items[].id`; внешний ID поставщика не используется в маршруте.
- На странице игры корректно видны все доступные поля, оценки по отдельным источникам и понятные состояния для отсутствующих данных.
- Отзывы загружаются по внутреннему ID, отображают `total` отдельно от количества полученных `items` и не обещают пагинацию, которой нет в API.
- 404, 422, 502, 503, 500, пустые результаты и сетевые сбои не приводят к пустому экрану или необработанному исключению.
- Прямое открытие и перезагрузка маршрутов работают; страница пригодна для мобильной ширины и доступна с клавиатуры.
- `npm run test`, проверка типов, `npm run build` проходят; локальный сценарий проверен с backend на `http://127.0.0.1:8000`.

## 9. Ограничения, которые сохраняются до расширения API

- Поиск не имеет offset/cursor-пагинации и сейчас ограничен фактической выдачей RAWG.
- Для отзывов есть только параметр `limit`, без страницы или курсора; можно получить до 100 элементов одним ответом.
- Данные Steam могут отсутствовать при неудачном сопоставлении или временной недоступности поставщика.
- Нет контрактов для авторизации, аккаунтов, избранного, рекомендаций и AI-функций; добавлять эти сценарии можно после появления соответствующих API-эндпоинтов.
